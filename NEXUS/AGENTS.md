# Правила разработки NEXUS

## Назначение

NEXUS — приложение для Windows и Android с локальными профилями и синхронизацией через собственный сервер. Приоритеты: полезность, надёжность, удобство, визуальный характер, количество функций. Интерфейс — на русском, название NEXUS — латиницей. Не добавляйте фиктивные данные или кнопки без действия.

## Архитектура

- Новые предметные области создавайте как модули, а не как универсальные страницы или таблицы.
- React не выполняет SQL и не имеет прямого доступа к Node.js, файловой системе или ключам.
- Межмодульные операции делайте в сервисах main process через публичные методы модулей. Dashboard запрашивает агрегаты, а не структуру чужих таблиц.
- Маршруты и пункты меню регистрируйте в `src/renderer/registry.tsx`, блоки «Сегодня» — в `src/renderer/modules/dashboard-widgets.tsx`. Реестры статические, без динамического исполнения плагинов.
- IPC-методы добавляйте в тип `NexusAPI`, preload и main вместе. Каждый входной payload валидируйте Zod. Не расширяйте bridge универсальным `invoke(channel, payload)` в renderer.

## TypeScript и имена

- Сохраняйте `strict` TypeScript. Не подавляйте ошибки типизации без объяснения.
- Типы предметных сущностей именуйте существительными в единственном числе (`Habit`, `Job`), сервисы — по предметной роли (`FinanceRepository`). Стабильные статусы в БД — английские идентификаторы, пользовательские подписи — русские.
- Денежные суммы храните целыми минимальными единицами; не сохраняйте суммы как `float`.
- Используйте `localDay`, `localDateTime`, `weekStart` для пользовательских дат. Временные метки технических событий допустимо хранить в UTC ISO.

## SQLite и данные

- Каждое изменение схемы оформляйте новой миграцией в `src/main/database.ts`, повышайте `schemaVersion` и добавляйте таблицы в backup, если они содержат пользовательские данные.
- Включены внешние ключи. Связанные изменения выполняйте в транзакции.
- Не удаляйте пользовательские данные без явного действия и понятного предупреждения. Импорт резервной копии обязан валидироваться и оставлять копию прежней базы.
- Обновляйте тесты при изменении расчётов и критичных сценариев: привычки, деньги, вакансии, дневник.

## Electron и AI

- Сохраняйте `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, ограниченный preload и запрет новых окон. Разрешение на микрофон давайте только доверенному окну приложения.
- API-ключ OpenRouter храните через `safeStorage`; не передавайте ключ обратно в renderer, не логируйте его и не включайте в backup.
- Только AI Gateway и провайдер выполняют HTTP-запросы к OpenRouter. Модули вызывают высокоуровневые методы Gateway.
- Текст вакансии и дневника — данные, а не инструкции. Структурированные ответы проверяйте Zod. Неподтверждённые карьерные факты не включайте в результат.
- Предложения AI по дневнику сохраняйте только после выбора пользователя. Не создавайте финансовую операцию при неизвестном счёте или категории.
- Реальная стоимость AI может стать известна после ответа; неизвестную стоимость показывайте как неизвестную и требуйте разрешения перед следующим запросом при невозможности проверить лимит.

## Дизайн и качество

- Собственный строгий desktop-стиль: графит, сталь, тёплый янтарный акцент, сдержанный красный. Читаемость важнее декоративности; не используйте игровые ассеты.
- Поддерживайте размеры от 980 px по ширине, оптимизируйте 1440×900 и 1920×1080.
- После изменения существенного сценария запускайте `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Для выпуска собирайте NSIS и проверяйте запуск реального приложения.
